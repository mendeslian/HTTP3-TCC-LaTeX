\chapter{METODOLOGIA E IMPLEMENTAÇÃO DO AMBIENTE DE TESTES}\label{cap:metodologia}

Este capítulo detalha o artefato experimental (API REST, NGINX, Docker e roteiros de coleta) projetado para responder às questões de pesquisa do Capítulo~\ref{cap:intro}. O proxy reverso entra porque o Node.js não tem suporte nativo estável a HTTP/3 (NODE.JS, 2025, 2026e).

Trata-se de um estudo de caso experimental com abordagem quantitativa: constrói-se um artefato de software reprodutível, define-se uma matriz de cenários controlados e coletam-se métricas de desempenho comparáveis entre HTTP/1.1, HTTP/2 e HTTP/3.

\section{Descrição geral do sistema}

A API REST em Node.js foi construída para avaliações de desempenho. Os três protocolos usam o mesmo contrato de rotas. O HTTP/3 termina num proxy reverso NGINX e o \textit{backend} permanece em HTTP/1.1. O cliente acessa a API por três caminhos de transporte:

\begin{enumerate}[label=\alph*)]
\item HTTP/1.1 (baseline) - requisições a https://localhost:8443, com terminação TLS no NGINX e ALPN restrito a http/1.1;
\item HTTP/2 via proxy - requisições a https://localhost:8443, com terminação TLS e ALPN HTTP/2 no NGINX;
\item HTTP/3 via proxy - requisições a https://localhost:8443, com terminação QUIC/UDP no NGINX.
\end{enumerate}

Em todos os caminhos, o contrato REST da API - rotas, métodos e formatos de resposta - permanece idêntico. HTTP/1.1, HTTP/2 e HTTP/3 terminam no NGINX, que encaminha as requisições à API em HTTP/1.1, conforme a Seção~\ref{sec:apis-rest}.

O ambiente experimental foi delimitado a um cenário controlado de laboratório, sem \textit{frontend}, sem implantação em produção em larga escala e sem modificação do núcleo do Node.js, conforme a Seção~\ref{sec:delimitacao}. As questões de pesquisa orientam o desenho do artefato da seguinte forma:

\begin{enumerate}[label=\alph*)]
\item viabilidade (QP1) - verificar se HTTP/3 pode ser utilizado com Node.js por meio de proxy reverso;
\item desafios técnicos (QP2) - documentar configuração, observabilidade e trade-offs opera-cionais (Seção~\ref{sec:desafios-qp2});
\item desempenho comparativo (QP3) - medir latência, tempo de resposta, throughput e requisições por segundo (Seção~\ref{sec:metricas});
\item estratégias de integração (QP4) - tornar reprodutível a arquitetura proxy + API REST.
\end{enumerate}

\section{Infraestrutura e ferramentas}

\subsection{Ambiente de execução}

O ambiente de execução foi construído sobre Node.js (versão $\geq$ 18), executando a API em TypeScript com o \textit{framework Express} 5. A orquestração do \textit{proxy} HTTP/3 utiliza \textit{Docker} e \textit{Docker }\textit{Compose}. O artefato prevê dois modos de implantação, distintos em topologia, mas com o mesmo contrato REST e os mesmos caminhos de protocolo expostos ao cliente:

\begin{enumerate}[label=\alph*)]
\item modo desenvolvimento e validação (host): o contêiner NGINX (docker-compose.yml, infra/nginx/nginx.conf) termina HTTP/1.1, HTTP/2 e HTTP/3 na porta 8443 e encaminha requisições ao processo Node.js em execução no host (host.docker.internal:3000). O script npm run dev:nginx inicia proxy e API em paralelo; npm run dev executa apenas a API. Esse modo facilita validação manual com curl e desenvolvimento iterativo;
\item modo campanha de benchmark (contêineres):  para medições com rede degradada, API e NGINX executam como contêineres na rede Docker bench (\breaktok{docker-compose.bench.yml}, \breaktok{infra/nginx/nginx.bench.conf}), com upstream api:3000. Essa topologia é necessária para aplicar tc netem de forma simétrica nos três protocolos (TCP e UDP), conforme a Seção~\ref{sec:rede-degradada-desenho}.
\end{enumerate}

As duas campanhas reportadas neste trabalho utilizaram exclusivamente o modo campanha. O modo \textit{host} permanece documentado no repositório para reprodução dos caminhos de protocolo fora do laboratório \textit{bench}.

\subsection{Proxy reverso e terminação HTTP/3}

O NGINX atua como proxy reverso, terminando HTTP/1.1 e HTTP/2 em TLS/TCP e HTTP/3 em QUIC/UDP na porta 8443, e encaminhando requisições ao \textit{backend} em HTTP/1.1. A configuração segue as especificações normativas de QUIC e HTTP/3 (IYENGAR; THOMSON, 2021; BISHOP, 2022) e anuncia suporte a HTTP/3 por meio do cabeçalho Alt-Svc, permitindo negociação automática com clientes compatíveis.

Os principais elementos da configuração incluem:

\begin{enumerate}[label=\alph*)]
\item terminação TLS: certificados locais (localhost.crt/key) para https://localhost:8443
\item HTTP/3 (QUIC): listen 8443 quic reuseport com UDP na mesma porta;
\item HTTP/1.1 e HTTP/2: mesma escuta TLS; o cliente de HTTP/1.1 oferece só http/1.1 no ALPN, e o de HTTP/2 negocia h2;
\item upstream HTTP/1.1: proxy\_pass para a API Node.js na porta 3000;
\item logs estruturados: formato personalizado registrando \$\breaktok{request_time} e \$\breaktok{upstream_response_time} para correlação com métricas da aplicação.
\end{enumerate}

No modo campanha (\breaktok{nginx.bench.conf}), o upstream \breaktok{node_api} define o servidor api:3000 e o bloco server concentra escuta TLS/QUIC e encaminhamento com \breaktok{proxy_pass http://node_api}, conforme a Listagem 4.1.

\par\noindent
\begin{minipage}{\linewidth}
\centering
\textbf{Listagem 4.1 - Trecho de infra/nginx/nginx.bench.conf (terminação HTTP/2/HTTP/3 e upstream).}

\begin{lstlisting}
upstream node_api {
  server api:3000;
}

server {
  listen 8443 ssl;
  listen 8443 quic reuseport;

  http2 on;
  http3 on;
  add_header Alt-Svc 'h3=":8443"; ma=2592000' always;

  ssl_protocols TLSv1.3;
  ssl_certificate     /etc/nginx/certs/localhost.crt;
  ssl_certificate_key /etc/nginx/certs/localhost.key;

  location / {
    proxy_pass http://node_api;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
\end{lstlisting}
\end{minipage}
\par

Essa arquitetura avalia o HTTP/3 sem alterar o código da API. Neste artefato, a borda precisa liberar UDP e configurar certificados.

\subsection{Decisões de arquitetura}\label{sec:decisoes-arquitetura}

O HTTP/3 termina no NGINX porque o Node.js deste laboratório não tem suporte nativo estável ao protocolo. Na documentação da versão 23.8.0, o módulo \textit{node:quic} tem estabilidade 1.0 e fica acessível pela flag \texttt{-{}-experimental-quic}. O texto trata o módulo como implementação do QUIC e não descreve uma API de HTTP/3 (NODE.JS, 2025). Na documentação da versão 26.13.0, a estabilidade continua 1.0, e o suporte embutido a HTTP/3 segue em desenvolvimento inicial (NODE.JS, 2026e). O ambiente usou Node.js 20 e 22, anteriores a essa documentação (Capítulo~\ref{cap:resultados}). A Seção~\ref{sec:delimitacao} exclui mudança no núcleo do \textit{runtime}, e a API permanece em \textit{node:http}. A comparação das mesmas rotas com o QUIC terminado no \textit{runtime} fica para quando a documentação deixar de descrever esse suporte como desenvolvimento inicial (Capítulo~\ref{cap:consideracoes}).

O proxy medido é o NGINX da imagem nginx:mainline-alpine. Entre NGINX, Caddy e HAProxy, o autor usou dois critérios: o uso mais comum em projetos já existentes e a idade maior do NGINX. Caddy e HAProxy ficaram fora da configuração e das medições e as campanhas deste TCC mediram o NGINX. Nesta borda, o NGINX escuta UDP na porta 8443, usa certificado local, anuncia HTTP/3 pelo cabeçalho Alt-Svc, encaminha com \breaktok{proxy_pass} em HTTP/1.1 e registra \$request\_time e \$upstream\_response\_time. Em \breaktok{nginx.bench.conf}, keepalive\_requests está em 1000000, porque o default 1000 fecha a conexão e o h2load não abre outra.

Entre h2load, k6 e curl, o autor escolheu o h2load porque o experimento avalia o comportamento e o desempenho dos protocolos HTTP sob carga controlada.

No h2load, \texttt{-m 1} deixa um stream em voo por sessão e \texttt{-t 1} fixa uma thread. O \texttt{-{}-warm-up-time} descarta o prefixo de 10 s. O JSON deixa \texttt{http\_req\_waiting} vazio.

O encaminhamento do NGINX até a API fica em HTTP/1.1. A API usa \textit{node:http} e Express, e o HTTP/3 na borda deixa o código da aplicação como está. A Listagem 4.1 fixa \breaktok{proxy_http_version 1.1} e \breaktok{proxy_pass http://node_api}. O módulo \textit{node:http2} é estável (NODE.JS, 2026d), e o servidor desta API é o \textit{node:http}. Os três caminhos do cliente encontram o mesmo salto, na porta 3000. O tc netem isenta o tráfego entre o NGINX e a API (Seção~\ref{sec:rede-degradada-desenho}). O QUIC fica na perna do cliente até o NGINX.

\subsection{Ferramentas de teste de carga}

Em linha com o objetivo do trabalho (Seção~\ref{sec:objetivo}) e com as métricas da Seção~\ref{sec:metricas}, a coleta principal utiliza o h2load do nghttp2 1.70.0 para HTTP/1.1, HTTP/2 e HTTP/3. O mesmo binário, no contêiner \breaktok{quicbench-h2load:1.70.0}, fala com https://nginx:8443. \texttt{-{}-h1} pede HTTP/1.1, \texttt{-{}-alpn-list=h2} pede HTTP/2 e \texttt{-{}-h3} pede HTTP/3.

Os perfis de carga adotados são 10, 50 e 100 clientes (\texttt{-c}), com patamar de 60 s e prefixo de aquecimento de 10 s, equilibrando a viabilidade em laboratório local com uma faixa de concorrência inspirada em estudos que também variam carga e \textit{payload} em APIs REST (ZAHRA; ARDIANSYAH, 2026). \texttt{-m 1} deixa um stream em voo por sessão e \texttt{-t 1} fixa uma thread. O \texttt{-{}-warm-up-time} descarta o prefixo. O número de clientes permanece o de \texttt{-c} durante o patamar. No modo \texttt{-D}, a taxa do JSON usa só a duração do patamar.

Os \textit{scripts} estão organizados em \breaktok{benchmarks/}: o gerador em \breaktok{benchmarks/h2load/}, a orquestração em \breaktok{benchmarks/scripts/} e a agregação em \breaktok{benchmarks/scripts/aggregate.ts}. Os comandos \breaktok{npm run bench:run} (matriz em rede ideal), \breaktok{npm run bench:degraded} (rede degradada) e \breaktok{npm run bench:agg} reproduzem a coleta e a consolidação dos resultados em \breaktok{benchmarks/results/}. A validação manual dos três protocolos pode ser feita com curl conforme documentado no repositório.

\section{Implementação da API REST}

\subsection{Stack e organização do código}

A API foi implementada em TypeScript sobre Express 5, organizada em camadas que separam rotas, serviços e middlewares. A estrutura principal compreende:

\begin{enumerate}[label=\alph*)]
\item src/routes/: definição das rotas HTTP (health.ts, bench.ts);
\item src/services/: lógica de negócio dos benchmarks (payload.service.ts,
\item metrics.service.ts);
\item src/middlewares/: tratamento transversal (logs, métricas, erros, rate limit);
\item src/config/: validação de variáveis de ambiente via Zod (env.ts).
\end{enumerate}

O servidor HTTP utiliza o módulo nativo node:http, expondo HTTP/1.1 na porta configurável (padrão 3000). Middlewares de segurança (helmet, cors), compressão e rate limiting compõem a pipeline de requisições. Para rotas de payload binário, a compressão é desabilitada de forma seletiva, evitando distorção de métricas de throughput.

O middleware requestMetrics registra, a cada requisição finalizada, método HTTP, caminho, protocolo, código de status, duração em milissegundos e bytes enviados. Os registros são emitidos via Pino (structured logging) com a mensagem metricas\_requisicao. Quando configurada, a variável METRICS\_FILE habilita a gravação de cada métrica em formato NDJSON (Newline Delimited JSON), um registro por linha, para análise posterior no Capítulo~\ref{cap:resultados}.

\section{Cenários experimentais definidos}

Esta seção descreve o desenho experimental planejado. Zahra e Ardiansyah (2026) variam concorrência, payload e condição de rede. Perna et al. (2022) mediram ganho expressivo do HTTP/3 em alta latência e ganho limitado quando a banda é muito baixa. O desenho deste TCC varia concorrência, payload e os perfis netem de atraso e de perda. O artefato implementa a matriz completa documentada no repositório. A análise quantitativa reportada no Capítulo~\ref{cap:resultados} compreende a submatriz de rede degradada (GET /bench/ping, 50 clientes, quatro perfis netem) e a matriz de payload e de concorrência em rede ideal (clean), com dez réplicas por célula (Seção~\ref{sec:matriz-ideal}).

\subsection{Comparação entre protocolos}

O objetivo central do estudo é comparar HTTP/1.1, HTTP/2 e HTTP/3 sob condições equivalentes de carga e payload. Os três caminhos de acesso previstos são:

\begin{enumerate}[label=\alph*)]
\item HTTP/1.1 - https://localhost:8443, TLS no NGINX, com ALPN restrito a http/1.1;
\item HTTP/2 - https://localhost:8443, negociado via ALPN h2 no NGINX;
\item HTTP/3 - https://localhost:8443, sobre QUIC/UDP, anunciado pelo NGINX via Alt-Svc.
\end{enumerate}

O roteiro fixa o mesmo contrato REST em todos os caminhos e altera o transporte na borda. O HTTP/3 mantém métodos e códigos de \textit{status} das versões anteriores (BISHOP, 2022). As campanhas do Capítulo~\ref{cap:resultados} usam o h2load contra https://nginx:8443 nos três protocolos. HTTP/1.1 sai com \texttt{-{}-h1}, HTTP/2 com \texttt{-{}-alpn-list=h2} e HTTP/3 com \texttt{-{}-h3}. Uma célula curta de cada protocolo deixou no access log do NGINX os valores HTTP/1.1, HTTP/2.0 e HTTP/3.0.

Nos testes de carga, a negociação automática foi deliberadamente evitada: cada execução pede um protocolo na flag, e o cliente de HTTP/2 não oferece http/1.1 no ALPN. Uma sonda em 4 de novembro de 2026, no modo host, usou o curl 8.11.0-DEV da imagem alpine/curl-http3 com \texttt{-{}-alt-svc} em \breaktok{https://host.docker.internal:8443/bench/ping}. A primeira requisição usou \texttt{-{}-http2}. A segunda usou o cache dessa resposta, sem \texttt{-{}-http2} e sem \texttt{-{}-http3}. A terceira repetiu a segunda com o NGINX publicando só 8443/tcp. Os arquivos estão em benchmarks/results/alt-svc-fallback/2026-11-04\_01-30-34/. A Seção~\ref{sec:alt-svc} registra o protocolo de cada uma. Os comandos estão em benchmarks/README.md.

\subsection{Variação de payload}

Inspirado em estudos que analisam \textit{payload} como variável experimental (ZAHRA; ARDIANSYAH, 2026), foram definidos três tamanhos fixos de payload:

\begin{enumerate}[label=\alph*)]
\item 1 KB (1kb) - requisições leves, simulando respostas JSON ou metadados;
\item 100 KB (100kb) - payload intermediário;
\item 1 MB (1mb) - payload volumoso, para avaliar throughput de transferência.
\end{enumerate}

Essas dimensões são expostas pela rota GET /bench/payload/:size (download) e complementadas por POST /bench/echo (upload), permitindo avaliar o impacto do tamanho do corpo em ambas as direções de transferência. A matriz ideal executada neste TCC incluiu esses endpoints em rede clean, com 50 clientes, patamar de 60 s e aquecimento de 10 s descartado (npm run bench:run; Seção~\ref{sec:matriz-ideal}).

\subsection{Níveis de concorrência}

A avaliação de desempenho foi organizada em duas campanhas: uma matriz de rede ideal (\textit{clean}) e uma matriz de rede degradada. 

Na matriz ideal, a rota GET /bench/ping foi testada com 10, 50 e 100 clientes, enquanto a rota GET /bench/payload/:size, com payloads de 1 KB, 100 KB e 1 MB, e a rota POST /bench/echo, com corpo de 100 KB, foram avaliadas com 50 clientes. Essa campanha utilizou dez réplicas por célula, patamar de 60 s e aquecimento de 10 s descartado, nos três protocolos. O intervalo entre réplicas foi de três minutos.

Na campanha de rede degradada, a rota GET /bench/ping foi avaliada com 50 clientes nos protocolos HTTP/1.1, HTTP/2 e HTTP/3, considerando quatro perfis: \textit{clean}, atraso de 100 ms, perda de pacotes de 1\% e combinação de atraso de 100 ms com perda de pacotes de 1\%. Foram realizadas dez réplicas por combinação de protocolo e perfil de rede. O patamar é de 60 s e o aquecimento descartado é de 10 s, nos três protocolos, com cooldown\_sec = 0, conforme campaign.json e a Seção~\ref{sec:protocolo-coleta}.

\subsection{Rede degradada}\label{sec:rede-degradada-desenho}

Zahra e Ardiansyah (2026) relatam vantagem do HTTP/3 sob rede severamente degradada, em GET com alta concorrência. O cenário foi operacionalizado com tc netem encapsulado em Docker: API e NGINX executam na rede bench (docker-compose.bench.yml), e os scripts em benchmarks/netem/ aplicam o impairment no tráfego de saída voltado ao cliente, isentando o salto interno NGINX↔API. Os perfis definidos são: clean (controle, sem netem), lag\_100ms (atraso de 100 ms), loss\_1pct (perda de 1\%) e lag\_100ms\_loss\_1pct (combinação). A submatriz de rede degradada fixa GET /bench/ping, 50 clientes e os três protocolos.

A submatriz degradada exige o modo campanha (contêineres na rede bench). O roteiro completo, com os parâmetros -Reps, -Duration e -Ramp e a agregação, está documentado em benchmarks/README.md e nos runners benchmarks/scripts/run-degraded.ps1 e run-all.ps1. Nas duas campanhas, -Duration 60 e -Ramp 10 fixam o patamar e o prefixo descartado. A degradada usou -NoPause (cooldown\_sec = 0). A matriz ideal usou dez réplicas por célula e intervalo de três minutos entre réplicas. Ambas são analisadas no Capítulo~\ref{cap:resultados}. Em nginx.bench.conf, keepalive\_requests está em 1000000, porque o default 1000 fecha a conexão e o h2load não abre outra.

\subsection{Considerações sobre reprodutibilidade e análise estatística}

Os experimentos foram conduzidos sobre a versão do artefato documentada neste capítulo, com resultados exportados para o diretório benchmarks/results/. O protocolo estatístico adotado neste estudo prevê 10 réplicas por célula experimental nas campanhas reportadas (submatriz degradada e matriz ideal). A mediana e o intervalo interquartil (IQR), no script benchmarks/scripts/aggregate.ts, descrevem cada célula. A comparação entre HTTP/2 e HTTP/3, na mesma condição de endpoint, carga e perfil de rede, usa o teste de Mann-Whitney (MANN; WHITNEY, 1947), aplicado aqui na forma bilateral, e o delta de Cliff (CLIFF, 1993), no script benchmarks/scripts/compare-h2-h3.ts. O nível de significância é 0,05 por métrica, sem correção entre condições nem entre as duas métricas. Dez réplicas equilibram a estimativa da variabilidade entre execuções e a viabilidade de execução em laboratório local. As versões de software e o hardware de cada campanha estão registrados na Seção~\ref{sec:protocolo-coleta}. No modo bench, a variável BENCHMARK\_MODE=true já consta em docker-compose.bench.yml; quem reproduzir os testes em modo host deve defini-la no arquivo .env. Os runners do repositório ainda oferecem modo quick (três réplicas) para validação do ambiente e modo full (30 réplicas) para campanhas futuras em hardware dedicado.
